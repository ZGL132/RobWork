## Problem

2026-10-17 手工验证在真实宿主上连续暴露装配层缺陷（草稿源未挂接、桥生命周期不闭合、异常穿透致整站退出）。复盘结论：现有验证对组件行为覆盖较多，**对生产装配完备性、跨组件生命周期、失败后状态一致性覆盖不足**——组件级测试全绿（内存闭包当磁盘、fake 模块、harness 演示绑定），组合正确性无自动化把守；注释声称的装配事实（"随装配挂接"）无调用点佐证且被读者（含 AI 会话）当事实引用。

## Decision

四条加固（修正版——首版草案中计数式门禁与"统一 catch 重试"经评审否决，见 Alternatives）：

1. **装配完备性门禁**：断言"当前产品配置下的必需模块 ID 集合 == 真实生产装配入口实际注册的模块 ID 集合，且无重复注册"，并对注册结果逐模块验证保存/恢复；不做实现类数量 vs 调用次数比较。attach/detach/switch 文本配对仅作审查线索不作门禁。
2. **异常隔离边界策略**（入 units/ui.md）：fail-fast 保留在内核/桥内；打开/关闭/切换操作边界与 Qt 回调边界负责捕获——三要素：捕获边界、回滚责任（诊断保留＋补偿清理）、恢复成功条件（回到"旧项目完整"或"干净无项目"并验证）；仅恢复确认后提示可重试，状态不可确认则停用相关操作走显式故障处置。
3. **真实宿主 E2E 冒烟**：五场景（同进程关/重开、A→B 切换三态、草稿保存恢复、应用后修订恢复、保存/释放失败）作为集成批次 DoD；杀进程恢复只承诺最后一次成功持久化的草稿；测试必须复用真实生产装配，禁止夹具自行接线。
4. **V 矩阵必验项 owner 化**：当前交付范围必验项挂 owner＋执行阶段/截止点＋状态＋证据；延期须明确风险接受人与补验条件；产品交付时不得无限期悬空（既有 T05/T08 追溯与 GTEST_SKIP 登记保留，补的是"集成节点交付阻断"这半边）。

附：装配性断言注释必须带可核对锚点（调用点或承接任务号），否则按废注释打回。

## Alternatives considered

（本 Note 起草过程中的真实备选——首版草案被 2026-10-17 二轮评审修正的部分）

1. **实现类数量 vs attachModule 调用次数的门禁**——否决：循环内一次调用可挂多模块；实现类可能含可选模块/平台差异/测试替身；数量相等也可能重复挂 A 漏挂 B。改为集合一致性断言。
2. **协议层统一"catch→弹窗→返回 false→继续使用"**——否决：异常抛出前状态可能已部分更新，盲目重试把显性失败变成后续数据错误。改为三要素（边界/回滚/恢复条件）。
3. **E2E 单场景"编辑→应用→关闭→重开→草稿恢复"**——否决：混合了草稿与正式修订两种持久化语义（应用成功后草稿可能已清理）。改为五场景分列。
4. **"有 attach 无 switch 调用即报警"作硬门禁**——否决为审查线索：关闭再开可合法走 detach→attach；switch 仅保留旧呈现的切换需要。约束对象是业务路径状态转换与失败回滚。

## Consequences

- 装配缺口从"人工随缘发现"变为"机器断言＋集成节点阻断"；
- E2E 需要可用的 Windows 桌面环境（CI 侧成本与稳定性需评估，可先半自动＋留痕）；
- 注释纪律收紧后，存量装配性注释需随批补锚点（登记欠账，不溯及重写）；
- 必验项 owner 化使交付前欠债显性化——延期要有具名的风险接受人。

## Verification

- 门禁①落地后：构造"漏挂 requirements"的装配应使测试失败（负例先行）；
- E2E③：S1~S5 场景在修复 F-910/F-911 前后各跑一轮（前＝复现证据，后＝修复验收）；
- 策略②：入 ui.md 后按 rule-enforcement 分级登记（review 层）并进 ACC 核查清单。
