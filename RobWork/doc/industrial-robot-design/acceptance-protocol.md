| 角色定义 | **实施者**＝领取契约的实现会话；**验收者**＝独立上下文的对抗式核查会话；**所有者**＝维护者（合入决策与语义裁决）＋文档链登记的各所有者（架构/需求/单元详设所有者） |

## 1. 触发条件

实施者在 `wp<nn>-t<kk>` 分支完成实现并推送 `origin`，自查项（双模式构建、测试执行留痕、文档同步、commit 四段式）全部就绪后，发出**验收请求**，内容固定为：任务 ID、分支名、commit 范围（base..head）、证据位置（构建日志 / gtest XML / ird-test-report.json / 留痕文件路径）。**实施者不得自行合入 `redesign-main`。**

## 2. 验收者的独立性要求（缺任一项即验收无效）

1. **全新上下文**：不与实施者共享任何会话记忆；只读代码、任务契约、设计文档与留痕。
2. **禁止读取实施叙述**：不消费实施者的过程说明/辩护文本，一切结论以产物与证据为准。
3. **对抗式立场**：目标是为"不通过"找证据，而非确认通过；每项检查要么给出通过证据（命令输出/文件行号），要么给出失败证据。
4. **复现优先于采信**：构建与测试必须由验收者亲手重跑，不引用实施者的运行结果。

## 3. 验收执行环境

- 干净构建树：集成模式**重新配置**（含 `-DRWS_BUILD_INDUSTRIALROBOT=ON`，确认缓存 `:BOOL=ON`）；独立冒烟模式另配临时目录。
- `git fetch origin` 后切换到任务分支；diff 范围以验收请求中的 base..head 为准。
- 验证脚本：`validate-docs.ps1` / `validate-task.ps1 -TaskFile <契约>` / `verify-task.ps1 -TaskFile <契约>`。

## 4. 验收清单（逐项出证据，10 项）

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 4.1 | **改动范围** | base..head 间每个变更文件都在契约 `allowedFiles` 内；`forbiddenFiles` 零触碰；无未登记的框架源码改动（SA-02——patches/ 无新文件即无登记） |
| 4.2 | **可复现构建** | 集成模式（重新配置后）与独立冒烟模式均零错误；结论留日志路径 |
| 4.3 | **契约 verify 命令** | 逐条独立执行，全部成功 |
| 4.4 | **acceptance 条目** | 契约 `acceptance` 数组逐项核对，均有对应证据；**未执行的不得标注通过**（含 `ird_gates`：WP-01-T01 落地前必须如实标注"未执行——门禁未建成"） |
| 4.5 | **测试真实失败能力**（验证验证者） | 任选 ≥2 个断言，构造应失败输入确认测试确实会红（防止恒真测试）；无法构造时说明理由 |
| 4.6 | **架构红线** | AGENTS.md §5 八条逐条自查：零 Qt（计算内核）、无跨单元私有头、无业务域互链、无名称前缀拼接、权威归属正确等 |
| 4.7 | **注释规范** | 按 AGENTS.md §2 抽查全部新增/大改文件：文件头、类/函数 Doxygen 中文注释、§2.5 高危信息表（单位/坐标系/rad/所有权/线程/错误语义/确定性）——公共头全查，实现文件抽查 ≥3 个；缺任一必填项即不通过 |
| 4.8 | **文档同步** | 实现与任务卡零偏差，或偏差已按 DTB §5.4 登记（单元卡增量修订）；任务状态/追踪矩阵同步 |
| 4.9 | **commit 质量** | 标题格式 `[WP-nn-Tkk] 动词开头`；正文四段（What/Why/验证/影响面）齐备且验证结论与留痕一致（发现粉饰即不通过） |
| 4.10 | **留痕完整** | gtest XML＋ird-test-report.json＋构建日志落位；`phase-one-validation.log` 或 resultNote 已更新 |

## 5. 裁决输出与记录

- 产出 `pass` / `fail`，写入 `traceability/acceptance/<taskId>-<YYYYMMDD>.md`，含：verdict、逐项证据（4.1~4.10）、发现的问题清单（分级：阻断/建议）、验收者环境说明。
- **pass 判据**：4.1~4.10 全部通过且无阻断级问题；建议级问题可随验收记录留档，不阻塞合入。
- **fail 判据**：任一阻断级问题（范围越界、构建/测试不可复现、红线命中、注释缺失必填项、验收粉饰）。
- fail 时验收记录即为返工输入；实施者（新会话或原会话）按记录修复后**重新发起验收**（全量重跑，不做增量验收）。

## 6. 所有者环节

- **合入**：验收 pass 后，由所有者（维护者）决策合入 `redesign-main` 并推送；合入动作可委托任一会话执行，决策不可。
- **裁决**：实施/验收双方分歧、语义拿不准、O 项处置——登记 DTB §4 对应类别，由对应所有者裁决；裁决前任务停在 fail/pass 待决状态，不强行推进。
