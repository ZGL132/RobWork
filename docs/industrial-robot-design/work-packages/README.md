# 工作包实施计划

本目录包含 WP-00～WP-25 的交付计划。工作包把已接受的需求、架构契约和模块方案组织成可验证的交付范围、任务依赖、迁移步骤和退出条件；它不拥有产品需求、公共契约或模块内部算法语义。

> 文档治理基线：`IRD-D0-20260829`
> 默认状态：`Planned`

## 权威关系

```text
requirements + Accepted architecture + Accepted module design
  -> work package plan
  -> agent task cards
  -> implementation / verification / review evidence
```

工作包与上游冲突时保持 `Planned` 并停止细化。工作包不得通过重新描述公式、状态或字段来修补架构缺口；必须由上游所有者修正并完成消费者影响评审。

## 工作包状态

| 状态 | 含义 |
| --- | --- |
| `Planned` | 已登记范围，但前置契约或实施细节尚未全部接受 |
| `Ready` | 上游契约、模块方案、任务卡、验证命令和资源均满足入口门禁 |
| `Implementing` | 实现者正在独立 worktree 中执行任务 |
| `Verifying` | 独立验证者执行黑盒、边界、数值、GUI 或安全验证 |
| `Reviewing` | 独立评审者检查需求符合性、架构和代码质量 |
| `Integrated` | 全部退出条件和阶段门禁通过并合入集成分支 |

具体单任务状态和角色分离规则以 `development-task-breakdown.md` 为准。

## 进入 Ready 的门禁

1. 需求、架构契约、ADR 和模块方案均为当前 `Accepted` 版本；
2. 前置 WP 已交付明确版本的输入工件；
3. 任务 DAG 无环，任务卡与索引一一对应；
4. 拥有目录、允许修改文件、禁止依赖和公共接口所有者明确；
5. 每项任务具有失败、正常和边界测试及完整命令；
6. 迁移、删除、回滚和停止条件完整；
7. 需求到真实任务、测试、评审和证据的追踪闭合；
8. 文档验证、依赖扫描和代码基线路径检查通过。

## 维护规则

- 文件名固定为 `WP-XX-<topic>.md`，同一 WP 只能有一个当前计划；
- 工作包改变任务 ID、前置、交付或阶段时，必须同步任务卡索引和追踪矩阵；
- 公共契约变化先由其所有者处理，工作包随后更新，不得反向修改；
- 任务卡存在性不代表工作包已经 `Ready`；
- 阶段退出以测试、证据、迁移删除和独立评审为准，不以文档完成数量代替。
