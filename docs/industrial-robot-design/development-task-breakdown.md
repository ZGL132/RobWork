# 工业机械臂设计软件开发任务拆解总纲

> 文档状态：执行基线 v1.0
> 需求基线：`requirements.md` v0.4
> 代码基线：`3627db152bfd4b4b43cde52b52603515f9d69df1`
> 集成分支：`codex/industrial-robot-rebuild`
> 规划周期：9～12 个月
> 工作量口径：人周区间，包含实现、测试、独立评审和修正

## 1. 文档目的

本文把产品需求拆为可独立实现、独立验证、独立评审和安全集成的工作包。本文负责冻结全局边界与依赖；各工作包计划负责给出具体接口、任务顺序、测试命令和退出条件。

需求文件是产品行为的唯一权威。现有代码只作为算法、测试数据和历史行为证据来源，不约束新架构。现有实现与需求冲突时必须以需求为准；无法通过黄金测试证明正确性的旧实现不得迁移。

## 2. 固定开发原则

1. 在提交 `3627db1` 上建立隔离分支和 worktree，当前原工作区中的未提交代码不带入，也不删除。
2. 新产品代码统一放在 `RobWork/RobWorkStudio/src/rwslibs/industrialrobot/` 下，以新 CMake 目标构建；旧业务插件在迁移期间只读。
3. RobWork 和 RobWorkSim 原则上只通过稳定 API 使用。基础库缺陷必须有独立最小复现、回归测试和单独提交。
4. 平台契约先于业务插件。阶段 A 契约门禁未通过前，不得合并七业务域的产品实现。
5. 跨插件数据只使用稳定对象 ID；RobWork 设备作用域名称只由 `IRuntimeNameResolver` 生成和反解。
6. 碰撞、证据判定、状态、单位转换、诊断、传动映射等共享语义各自只有一个权威实现。
7. 业务插件只包含编辑入口、运行入口和结果解释；领域与计算核心不得依赖 Qt Widgets。
8. 每个任务按“实现—独立验证—独立评审—修正—集成”完成。同一执行上下文不得同时担任实现者和最终评审者。
9. 新功能替代旧链路后，在同一阶段删除旧目标、旧测试和无用依赖，不保留长期双轨。
10. P0 是对应发布切片的阻断条件；P1 仍有完整任务和验收定义，但允许排在 R2 之后。

## 3. 目标代码结构与依赖方向

```text
RobWork/RobWorkStudio/src/rwslibs/industrialrobot/
  core/                 工程数学、领域对象与公共状态
  project/              项目命令、修订、分支与持久化
  evidence/             快照、结果、证据和当前性
  runtime/              规范模型、名称映射、WorkCell/DWC 编译
  policy/               统一工程策略和共享碰撞评估
  execution/            调度、工作进程、缓存和检查点
  diagnostics/          诊断目录、本地化和日志策略
  io/                   安全导入导出与 CSV 目录包
  ui/                   会话状态、场景投影和公共 Qt 组件
  reporting/            ReviewReport 与 HTML/PDF/数据包
  plugins/
    modeling/
    requirements/
    kinematics/
    trajectory/
    dynamics/
    selection/
    optimization/
  testkit/              黄金数据、契约夹具、故障注入与性能基准
```

允许的依赖方向为：

```text
core
  → project / evidence / runtime / diagnostics / io
  → policy / execution
  → 各业务域计算核心
  → reporting
  → ui 与薄插件
```

任何反向依赖、业务插件间直接依赖、插件读取其他插件 Widget/私有文件，或 RobWork/RobWorkSim 反向依赖产品层，均为合并阻断项。

建议新目标使用统一前缀：`sdurws_ird_*`。旧 `sdurws_robotmodelbuilder`、`sdurws_engineeringrequirements`、`sdurws_kinematicanalysis` 和 `sdurws_structureoptimizer*` 不得成为新核心库的依赖。

## 4. 角色与合并流程

### 4.1 角色

| 角色 | 主要职责 | 不得承担 |
| --- | --- | --- |
| 工作包所有者 | 冻结公开接口、目录所有权和变更顺序 | 绕过需求追踪接受隐式行为变化 |
| 实现者 | 按 TDD 实现任务并运行模块测试 | 作为同任务最终评审者 |
| 独立验证者 | 依据需求和公开契约补充黑盒、边界、数值或 GUI 测试 | 依赖实现者的口头说明降低断言 |
| 独立评审者 | 需求符合性评审、架构与代码质量评审 | 直接改代码后自行批准 |
| 集成负责人 | 检查门禁、合并顺序和阶段状态 | 合并缺少验证或追踪的提交 |
| 产品/机械评审人 | 确认工程语义、阈值、证据和试点数据 | 以界面演示替代数值证据 |

### 4.2 单任务状态

```text
Planned → Ready → Implementing → Verifying → Reviewing
        → Rework → Verifying → Reviewing → Integratable → Integrated
```

存在需求歧义、公共契约未冻结、前置包未通过或黄金数据缺失时保持 `Planned`，不得进入实现。评审发现问题必须回到 `Rework`，不得由评审者在原提交上直接修补后批准。

### 4.3 分支与提交

- 集成分支：`codex/industrial-robot-rebuild`。
- 工作包分支：`codex/wp-XX-<topic>`。
- 一个可评审提交只解决一个需求簇或一个架构边界。
- 提交说明必须包含工作包 ID；合并说明必须列出需求 ID、测试 ID、评审结论和删除清单。
- 公共接口只能由其所有者工作包修改；消费者需要变更时先提交接口变更申请，由所有者更新契约和契约测试。

## 7. `.rwdesign` 与 CSV 目录包

项目采用目录式结构：

```text
ProjectName.rwdesign/
  HEAD
  project.json
  revisions/<revision-id>/
  objects/<sha256>/
  results/<run-id>/
  checkpoints/<run-id>/<attempt-id>/
  drafts/
  reports/
```

保存固定为“写入新版本和对象 → 完整校验 → 原子切换 HEAD”。旧 `.rwproj` 明确拒绝，不建设兼容层。首个正式 `.rwdesign` Schema 发布后，后续 Schema 变化必须提供前向升级器。

器件目录固定为：

```text
catalog/
  catalog_manifest.json
  motors.csv
  reducers.csv
  motor_curves.csv
  reducer_curves.csv
  compatibility.csv
```

任务坐标和器件目录首版只直接导入 CSV。CSV 按数据解析，不执行公式；导出对可能触发表格公式解释的文本字段统一转义，并在结构化证据中保留原始值。

## 8. 阶段与门禁

### 8.1 阶段 A：基础重建

- 交付 WP-00～12 的冻结契约、最小实现骨架和测试入口。
- A-GATE-01～07 全部通过。
- 公共接口、数据所有权、任务状态、诊断、快照、缓存、容差和名称/策略契约完成联合评审。
- 未通过时不得合并业务插件产品实现。

### 8.2 阶段 B：现有闭环重构

- 交付 WP-13～15 和 WP-20 的 OPT-B。
- 通过 MDL/REQ/KIN 全部 P0、AT-01～05、AT-15～18。
- 新机型与改型均形成“建模—需求—运动学—静态候选比较”闭环。
- 旧四插件主链路、旧格式和冗余适配退出构建与安装包。

### 8.3 阶段 C：动态设计链

- 交付 WP-16～19 与 WP-12 完整报告，形成 R1。
- 通过 TRJ/DYN/SEL 全部 P0、AT-06～08、AT-19 和冻结数值容差。
- 每个被淘汰器件至少给出稳定诊断码、实际值和阈值。

### 8.4 阶段 D：联合优化与规模化

- 交付 WP-21 与 WP-23 的规模化能力，形成 R2。
- 通过 AT-09～14 和全部 NFR-PERF 门禁。
- 硬约束失败、证据不足或 Partial 候选不得进入可行 Pareto 集。

### 8.5 阶段 E：试点与发布

- 完成 WP-22、24、25。
- 至少 1 台真实机械臂、1 类搬运任务和 5 名目标用户完成试点。
- 开放 Blocker 为 0；遗留 Critical 均有负责人、影响说明和计划日期。

## 10. 测试与追踪规则

1. `requirement-traceability.csv` 中每个需求 ID 必须恰好有一个主实现工作包，可以有多个支持工作包。
2. 每个 P0 拆为 Given/When/Then 断言；每个 P1 保留验收方法和目标阶段。
3. 数学与算法使用需求第 15.3 节冻结容差；模块不得自行扩大容差。
4. 核心算法必须有解析算例或独立参考实现；适配层必须有 RobWork/RobWorkSim 契约测试。
5. Windows GUI 测试在 Visual Studio x64 开发环境运行，设置 `QT_QPA_PLATFORM=windows`，一次只运行一个 GUI 测试可执行文件。
6. 本机脚本与 Windows GitLab Runner 执行同一构建、模型测试、GUI 测试、静态边界扫描和安装包测试。
7. 以下任一情况阻止合并或发布：P0 未通过、Blocker 未清零、追踪断裂、重复权威实现、非法依赖、未处理失败测试、旧目标仍进入发布包。

## 11. 工作包计划最小内容

每份分包计划必须包含：

- 目标、非目标、需求 ID 与阶段；
- 唯一拥有目录、允许修改文件和禁止依赖；
- 前置输入、公开输出、接口与数据流；
- 可独立合并的任务序列；
- 每个任务的实现步骤、失败测试、通过测试和提交边界；
- 输入错误、工程不可行和系统错误处理；
- 模块、契约、数值、GUI、性能或安全测试；
- 独立验证清单和独立评审清单；
