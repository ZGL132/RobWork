## 3. 权威变更流程

```text
提出变更
  -> 标识需求 ID / 契约 / 消费者
  -> 由权威所有者修改
  -> 必要时新增或替代 ADR
  -> 更新模块方案、工作包和任务卡
  -> 重新生成追踪矩阵
  -> 运行文档与代码边界校验
  -> 独立评审
  -> 状态变为 Accepted
```

禁止在消费者文档或实现中“临时解释”公共语义。紧急缺陷若需要改变需求或公共契约，也必须先完成最小 ADR、影响清单和回归测试，不得以代码提交替代决策记录。

## 4. 实施入口门禁

一个工作包或任务卡只有同时满足以下条件才能从 `Planned` 进入 `Ready`：

1. 引用的需求版本为当前 `Accepted` 版本；
2. 引用的架构契约和 ADR 均为 `Accepted`；
3. 所有前置 WP/Task 已完成并提供所需工件；
4. 允许修改、禁止修改和公共接口所有者明确；
5. 输入输出字段、单位、状态、错误和所有权可唯一推导；
6. 验证命令完整，不含省略号、占位路径或未登记目标；
7. 需求、真实任务、测试、评审和证据路径的追踪闭合；
8. 文档校验和代码基线路径检查通过；
9. 不存在仍需实现者自行决定的跨模块语义。

任一条件不满足时，任务保持 `Planned` 并报告阻塞，不得通过实现代码反向冻结设计。

## 5. D0 之后的受控优化顺序

1. D1：契约注册表、符号注册表和 ADR；
2. D2：规范运动学、评估语义、任务状态机、候选编译及持久化边界；
3. D3：机器可验证 Schema 和完整公共接口；
4. D4/D5：按依赖顺序完成平台与业务模块详细设计；
5. D6/D7：更新工作包并重写可独立执行的任务卡；
6. D8：建立真实任务和测试级双向追踪；
7. D9：增强自动校验并执行代表任务卡演练。

后续步骤可以提升文档版本和状态，但不得改变本基线规定的权威层次和冲突停止规则；确需改变时必须建立新的文档治理基线。
